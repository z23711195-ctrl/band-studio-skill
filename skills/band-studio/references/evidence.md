# 证据与交付状态

用简短标签或分栏即可，不要求每句都加标签。重点是在记录与报告中不混淆：

| 类型 | 依据 | 能说明什么 |
|---|---|---|
| 用户要求 | 当前对话或明确确认 | 必须保留/允许修改的内容 |
| 来源事实 | 可归属的来源与具体版本 | 目录、公开说明、该版本的信息 |
| 测量候选 | 工具、输入、范围、结果 | BPM/音高/和弦/分离/时码等候选 |
| 内容观察 | 实际接收并审阅的音频/视频/图片 | 对应范围内的所见所闻 |
| 创作提案 | 本轮新写的词、编配和设计 | 可供选择的方案，不是乐队既定风格 |
| 用户认可 | 明确反馈 | 该版本获认可的部分 |

建议任务记录字段：source_id、source_hash、source_range、preserve、change、version、outputs、checks、unverified、status。实际项目路径可以存本机记录，不进入公开示例。

`planned → running → produced → checked → user_accepted` 是不同状态；实际阻塞另记 `blocked_reason`，不丢弃已完成部分。只有用户反馈能产生 user_accepted。

## 验证覆盖

- `doctor.py` 检测可执行文件与滤镜，不测试账号授权、音频语义模型或云 API。
- `catalog.py` 做文件索引，可选哈希和技术探测，不证明听辨或原创。
- `verify_delivery.py` 检查格式与外置 SRT 时间范围，不证明字幕已烧入画面、每字同步、声音正确或审美满意。
- 模拟测试只验证程序行为。合成音频测试只证明特定样例的结果，不能推广成真实混录准确率。
- `jev.py` 对提供的文字做辅助判断。按 [evidence 模式](jev.md) 批量核查拟交付结论与证据，优先复核矛盾和不足项；它不产生新的媒体观察，也不将 `produced` 自动升级为 `checked` 或 `user_accepted`。

最终交付用简短说明写清：输出在哪里、实际做了什么、如何检查、仍未确认什么。失败必须指出发生在哪一层，不靠重试次数或工具数量装作完成。
